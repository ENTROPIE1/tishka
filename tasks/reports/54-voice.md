# 54. Голос в главном процессе (src/voice, src/main) — отчёт о поиске ошибок

Код не менялся. Все находки ниже прослежены по коду; четыре подтверждены временными тестами (текст приведён, тесты из репозитория удалены).

## Находки (по убыванию важности)

### 1. Ошибка распознавания посреди разговора снимает таймер ухода — режим разговора не закрывается по тишине

- **Файл:** `src/voice/wake-flow.ts:221` (сброс) и `src/voice/wake-flow.ts:196-207`, `223-230` (нет перевзвода).
- **Как проявляется:**
  1. Включён режим разговора (клик, горячая клавиша или имя при `talkByDefault`); таймер ухода на 30 секунд заведён.
  2. Человек говорит фразу, которую служба не распознаёт («Не расслышал») или служба отвечает ошибкой (недоступна, код 500).
  3. `handlePhrase` в начале обработки вызывает `clearTimer()`, а ветка ошибки в `transcribe()` просто вызывает `onMissedSpeech`/`reportError` и возвращается — `armTimer()` никто не вызывает (он вызывается только в `.finally` успешного `handleUserText`).
- **Что видит:** микрофон остаётся открытым неограниченно долго, предупреждение «скоро уйду» не приходит, режим не закрывается сам ни через 30 секунд, ни когда-либо. То же в чате: разговор висит вечно. Таймер теряется и после любой службы-ошибки, а не только «Не расслышал».
- **Подтверждение:** тест (падает на последней строке — режим остался включённым):

```ts
it('«Не расслышал» посреди разговора: таймер ухода потерян, режим не закрывается по тишине', async () => {
  const h = makeHarness([{ error: 'Не расслышал' }]);
  h.flow.enableConversation();
  await vi.advanceTimersByTimeAsync(10000);
  h.flow.handlePhrase(wav);
  await flush();
  expect(h.flow.isConversation()).toBe(true);
  await vi.advanceTimersByTimeAsync(60000);
  expect(h.flow.isConversation()).toBe(false); // FAIL: true — режим так и остался
});
```

- **Как исправить:** вызывать `armTimer()` в `finally` транскрипции в `handlePhrase` (во время ответа он уже защищён проверкой `answering` и просто не сработает), либо в ветках ошибки/несовпадения `transcribe()`.

### 2. После напоминания по расписанию микрофон отклика на имя отключается и не включается обратно (TTS выключен или недоступен)

- **Файл:** `src/main/pet-wake.ts:13` (BUSY), `73-85` (обработчик шины).
- **Как проявляется:**
  1. Включён отклик на имя; `voice.tts.enabled: false` (значение по умолчанию, `src/core/config.ts:27`) либо служба синтеза не отвечает.
  2. Срабатывает напоминание или навык по расписанию: ядро эмитит `wake(trigger)`, `notify`, `reply` и на этом заканчивает (`src/core/triggers/scheduler.ts:48-52`, `src/core/memory/review.ts:49-51`). Последующих `idle`/`speak.end` нет: `idle` эмитит только `processUserText`, `speak.end` — только очередь речи.
  3. Событие `reply` входит в BUSY → `busy = true`; сбросить его может только `idle` или `speak.end`, которых не будет.
- **Что видит:** после напоминания «Тишка» перестаёт откликаться на имя; значок микрофона потух; warmTimer каждые 15 секунд пересчитывает состояние с тем же `busy=true`. Оживить можно только вручную (клик/горячая клавиша/набрать текст). С включённым и работающим TTS флаг снимает `speak.end` — дефект виден именно при выключенном или неработающем синтезе.
- **Подтверждение:** тест (последняя проверка падает — `isListening()` остаётся `false`):

```ts
vi.mock('electron', () => ({ ipcMain: { on: vi.fn() } }));

it('напоминание (reply без последующих speak/idle): микрофон остаётся выключен', async () => {
  const bus = createEventBus();
  const wake = registerPetWake({
    pet: { wakeState: () => undefined } as never,
    flow: { conversationOwner: () => null, isLeavingSoon: () => false,
            handlePhrase: () => undefined, toggleConversation: () => undefined,
            escape: () => undefined, reportError: () => undefined } as never,
    bus,
    getVoice: () => voice({ wakeEnabled: true }),
    getWarmMinutes: () => 30,
    isReady: () => true
  });
  bus.emit({ type: 'idle' });
  expect(wake.isListening()).toBe(true);
  bus.emit({ type: 'wake', source: 'trigger' });
  bus.emit({ type: 'notify', title: 'Напоминание' });
  bus.emit({ type: 'reply', reply: { say: 'Напоминание' } });
  expect(wake.isListening()).toBe(false);
  await flush();
  expect(wake.isListening()).toBe(true); // FAIL: false — busy не снят, микрофон отключён
});
```

- **Как исправить:** в ядре после реплик триггеров (напоминания, обзор памяти, наблюдения) эмитить `idle`, как это делает `processUserText`; либо в `pet-wake`/`chat-talk` снимать busy также по событиям завершения триггерных цепочек.

### 3. «Не расслышал» или ошибка записи в одиночной записи не завершают состояние: busy остаётся включённым

- **Файл:** `src/main/pet-listen.ts:67-81`.
- **Как проявляется:**
  1. Человек говорит «Тишка» (обычная запись через окно-питомца), `listen.start` уже включил busy в `pet-wake`/`chat-talk`.
  2. После имени тишина 5 секунд → рекордер отдаёт `{ kind: 'nospeech' }` (или ошибка доступа к микрофону → `{ kind: 'error' }`).
  3. `handleResult` для `cancel` эмитит `idle`, а для `nospeech` и `error` — только событие `error`; никакого `idle` нет, busy не снимается.
- **Что видит:** микрофон прослушивания имени остаётся выключен после первой же неудачной записи до следующего ручного действия; в облачке — «Не расслышал», но значок не оживает даже после того, как ошибка ушла.
- **Подтверждение:** тест (падает — `idle` нет):

```ts
it('«Не расслышал» после одиночной записи: событие idle не приходит', () => {
  const bus = createEventBus();
  const events: TishkaEvent[] = [];
  bus.on((event) => events.push(event));
  const listen = createPetListen({
    bus,
    core: { handleUserText: async () => ({ say: 'ок' }) } as never,
    stt: { status: () => 'ready', transcribe: async () => ({ ok: true, text: 'тест' }) } as never,
    sendCommand: () => undefined
  });
  listen.toggle('click');
  listen.handleResult({ kind: 'nospeech' });
  expect(events.some((event) => event.type === 'idle')).toBe(true); // FAIL: idle нет
});
```

- **Как исправить:** в `handleResult` для `nospeech` и `error` эмитить `{ type: 'idle' }` так же, как для `cancel`.

### 4. На уведомление по триггеру Тишка вслух отвечает «Фыр. Слушаю.», хотя никто не звал и она не слушает

- **Файл:** `src/main/pet-speak.ts:117-119`.
- **Как проявляется:**
  1. Включён синтез речи; срабатывает напоминание, расписание навыка или обзор памяти — ядро эмитит `wake` с `source: 'trigger'` (например, `src/core/triggers/scheduler.ts:49`).
  2. Обработчик `wake` в `pet-speak` не смотрит на источник и ставит в очередь `CANNED.greeting` («Фыр. Слушаю.»), затем звучит и сам текст уведомления.
  3. `wake-flow.appear()` триггер намеренно игнорирует («уведомление не в счёт») — состояние прослушивания не включается.
- **Что видит:** колонка говорит «Слушаю» и затем уведомление, но режим разговора не включён и микрофон не открыт: обещание «слушаю» ложно. То же приветствие звучит, даже если служба распознавания не готова.
- **Подтверждение:** тест (падает — `speak.start` для триггера приходит):

```ts
it('уведомление по триггеру: не должно звучать приветствие «Слушаю»', async () => {
  const bus = createEventBus();
  const events: TishkaEvent[] = [];
  createSpeechOutput({
    bus,
    getConfig: () => fullConfig(), // tts.enabled: true
    play: () => new Promise<void>(() => undefined),
    fetch: (async () => new Response(new Uint8Array([1, 2, 3]), { status: 200 })) as unknown as typeof fetch
  });
  bus.on((event) => events.push(event));
  bus.emit({ type: 'wake', source: 'trigger' });
  for (let i = 0; i < 10; i += 1) await Promise.resolve();
  expect(events.some((event) => event.type === 'speak.start')).toBe(false); // FAIL: приветствие запланировано
});
```

- **Как исправить:** в обработчике `wake` в `pet-speak` планировать приветствие только при `source !== 'trigger'`.

### 5. На время калибровки чат продолжает слушать и отвечать

- **Файл:** `src/main/chat-talk.ts:45-55` (state), вместе с `src/renderer/chat/talk-mode.ts:40-61`.
- **Как проявляется:**
  1. В чате включён режим разговора (микрофон чата слушает).
  2. Человек открывает настройки и запускает калибровку; `VOICE_CALIBRATION` вызывает `chatTalk.setPaused(true)` — комментарий в `ipc-voice.ts:57-58` обещает, что «постоянное прослушивание и разговор приостанавливаются, чтобы микрофон не перехватывало другое окно».
  3. `chat-talk` шлёт `{ active: false, conversation: true }`, но talk-mode запускает и останавливает слушатель только по флагу `conversation` — поле `active` он игнорирует.
- **Что видит:** во время калибровки слушатель чата остаётся открытым и шлёт фразы; `flow.conversation` при паузе не сбрасывается, поэтому распознанная во время калибровки речь уходит в `handleUserText` — Тишка начинает отвечать посреди калибровки и мешает измерению шума.
- **Подтверждение:** только чтением кода (нужен jsdom-стенд рендерера): в `talk-mode.ts` `apply()` не использует `state.active`.
- **Как исправить:** в talk-mode запускать/останавливать слушатель по `active` (а не только по `conversation`), либо в `chat-talk` при паузе транслировать `conversation: false`.

### 6. Перезагрузка окна-питомца во время речи замораживает очередь речи и «занятость» навсегда

- **Файл:** `src/main/pet-speak.ts:31-35` (очередь) вместе с `src/main/index.ts:156-169` (play).
- **Как проявляется:**
  1. Тишка проговаривает реплику: очередь ждёт `play`, который резолвится только ответом `PET_SPEAK_DONE` из окна-питомца; таймаута нет.
  2. Посреди речи окно питомца перезагружается (`memory-watch` при превышении лимита памяти вызывает `pet.reload()`) или падает — ответ `speak-done` не приходит никогда.
  3. `play` не завершается → `run()` очереди стоит в `await` навсегда; `speak.end` не приходит, busy в `pet-wake`/`chat-talk` остаётся `true`.
- **Что видит:** Тишка замолкает до перезапуска приложения: новые реплики не проигрываются, а постоянное прослушивание не включается (active=false из-за залипшего busy) даже после истечения warm-времени. Воспроизводимо и без memory-watch: сбой рендерера в момент речи.
- **Подтверждение:** только чтением кода: единственный резолв обещания — `ipcMain.on(PET_SPEAK_DONE_CHANNEL)` (`index.ts:150-154`), отмены/таймаута нет.
- **Как исправить:** ограничить ожидание `speak-done` таймаутом (например, по длительности wav с запасом) либо резолвить очередь при `did-finish-load`/уничтожении содержимого окна-питомца.

### 7. Проверка службы может висеть минуты вместо 30 секунд: `probe` без таймаута

- **Файл:** `src/voice/stt-service.ts:110` (вызов), `src/voice/stt-http.ts:45-52` (probe).
- **Как проявляется:**
  1. В настройках адрес службы указан так, что TCP-соединение устанавливается, но ответ не приходит (недоступный хост, «полузакрытый» сокет).
  2. `waitReady` ждёт `await probe(...)`: у запроса нет `AbortSignal`, дедлайн 30 секунд проверяется только после возврата `probe`.
- **Что видит:** кнопка «Проверить» крутится не 30 секунд, а пока не отвалится сам fetch (для Node-фильтча — до минут на коннект/заголовки), затем «Служба распознавания не ответила за 30 секунд».
- **Подтверждение:** только чтением кода.
- **Как исправить:** передавать в `probe` `AbortSignal` с коротким таймаутом или гонять `probe` и дедлайн через `Promise.race`.

### 8. Двойной клик «Проверить»: первый ответ показывает «Запуск отменён» без вины пользователя

- **Файл:** `src/main/ipc-voice.ts:41-49`.
- **Как проявляется:**
  1. Служба стартует медленно; человек нажимает «Проверить» второй раз.
  2. Второй `start()` отменяет первый; обработчик первого канала возвращает `{ state: 'starting', error: 'Запуск отменён' }`.
- **Что видит:** в настройках мелькает ошибка «Запуск отменён», хотя пользователь ничего не отменял; через мгновение появляется результат второго запуска.
- **Подтверждение:** только чтением кода (поведение виднно из `stt-service.start` + `RunController.begin`).
- **Как исправить:** для перезапуска по кнопке не показывать ошибку `Запуск отменён` (это вытеснение новым запуском), а вернуть актуальное состояние службы.

## Что просмотрено и ошибок не найдено

- `src/voice/wake.ts` — сопоставление имени (в т.ч. искажения, склейки слов, латинские двойники), `withinOneEdit`, `isDismiss`, лимит длины имени из памяти; покрыто тестами, расхождений нет.
- `src/voice/stt-run.ts` — отмена запуска и ранний выход процесса корректны: `wake` снимается, повторный `begin` отменяет предыдущий, `stop` убивает только свой процесс (есть тесты).
- `src/voice/stt-http.ts` — таймаут запроса распознавания снимается в `finally`, копия буфера перед `Blob` корректна, ошибки сети превращаются в понятный результат.
- `src/voice/vad.ts` — окна шума/речи, `settleMs`, непрерывный режим, обрезка записи; проверены на граничных случаях тестами. Теоретический край `options.threshold === 0` (уровень в NaN/1) недостижим: калибровка хранит порог не меньше `MIN_THRESHOLD`, а конфиг по умолчанию — `null`.
- `src/voice/calibration.ts` — при плохом соотношении шум/речь порог может опуститься ниже `шум × 1,5`, но VAD при использовании подтягивает его (`threshold()` в vad.ts), видимого дефекта нет; качество при этом помечается `weak`/`bad`.
- `src/voice/warm.ts` — логика тёплого состояния согласована с использованием в `pet-wake`.
- `src/voice/tts-client.ts` — таймауты, коды ошибок, разбор ответа — ок.
- `src/voice/speech-queue.ts` — гонки `stop()` во время воспроизведения, `enqueue` во время `await play`, переполнение ожидания — обработаны корректно.
- `src/main/ipc-speech.ts` — тривиальные обработчики, ошибок нет.
- `src/main/pet-listen.ts:47-60` — `toggle` недостижим из рендерера (preload-метод `listenToggle` никем не вызывается): мёртвый код, не поведенческая ошибка; `handleResult` для `wav`/`cancel` корректен (кроме находки 3).
- `dispose()` в `pet-wake`/`chat-talk` не снимает обработчики `ipcMain.on` — слушатели регистрируются один раз на жизнь приложения, реальной утечки нет.

## Не считаю находками (проверено, отклонено)

- Сброс `.catch(() => undefined)` вокруг `core.handleUserText` в `wake-flow` и `pet-listen` — не «потерянная ошибка»: ядро само ловит ошибки, эмитит `error` и возвращает понятный reply (`src/core/app.ts:185-208`).
- Отбрасывание фраз во время ответа и хранение только последней отложенной фразы (`pending`) — зафиксировано тестами как намеренное поведение.
- Ошибка «Запуск отменён» у вытесненного запуска при рестарте из-за смены настроек (`ipc-settings` → `stt.stop/start`) — не показывается пользователю, состояние догоняет warm-таймер за 15 секунд.
